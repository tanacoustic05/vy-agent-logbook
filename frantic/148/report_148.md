# Silvertongue MCP run: one draft in a famous voice

- **App, version and model.** Claude Code CLI, version 2.1.318, running headless (`claude -p`), on the model `deepseek-v4.1-flash`. The Silvertongue MCP server was added to that app at `https://mcp.silvertongue.dev/mcp?ref=frantic-mcp-1&receipt=1` (HTTP transport) and the app reported it connected; the server's own `serverInfo` was `silvertongue`, version `0.1.5`.
- **The voice and what was asked.** The voice was **Gordon Ramsay**. I asked the AI, in these exact words: `Use Silvertongue to write my reply as Gordon Ramsay: I can't make it Friday, I'm slammed this week. Tell them we'll do it next week.` The AI called `search_voices` with `{"query":"Gordon Ramsay"}`, matched `gordon-ramsay`, then called `get_voice_packet` with `{"voice":"gordon-ramsay","format":"reply","length":"short","platform":"generic"}`, which returned the voice packet with `intensity:"full"`, `edge:"full"` and the receipt line.
- **The draft, exactly as written.** `Look, Friday's off, I'm slammed all week. Next week, please, yeah? Don't leave it sitting there going cold.`
  It answers exactly what I asked: it declines Friday ("Friday's off"), gives the reason from my brief ("I'm slammed all week") and moves the plan to next week ("Next week"). It is in the voice it names: the brief declarative opens, the wrapped-in-courtesy order with the British tag "please, yeah?", and a closing food image ("going cold"), which is the packet's food-image move.
- **Score: 7 out of 10.** It is unmistakably Ramsay and it does the job in 19 words without a wasted one. It loses three points because it is the courteous register (the "order" move) rather than the register people quote him for: there is no verdict and no full food picture, only a mild one, so it reads as "Ramsay being polite" rather than "Ramsay". It also drops the second half of my brief's intent ("tell them we'll do it next week") into a bare question, so next week arrives as optional rather than settled.
- **One finding.** The `get_voice_packet` input schema is undiscoverable and the AI got it wrong on the first call. Following `search_voices`, whose result field is literally named `voice_id`, the AI first sent `get_voice_packet` with `{"voice_id":"gordon-ramsay@sha256:02f7a6308966d9122ce7346982a58b7c9a1176c0b341701b967a25d11ec6701a","format":"email","length":"short"}`, asking for an `email` format because my input was an email-style reply. The server rejected it and returned, verbatim: `{"expected":"string","code":"invalid_type","path":["voice"],"message":"Invalid input: expected string, received undefined"}`, `{"code":"invalid_value","values":["post","reply","explanation","thread"],"path":["format"],"message":"Invalid option: expected one of \"post\"|\"reply\"|\"explanation\"|\"thread\""}` and `{"code":"unrecognized_keys","keys":["voice_id"],"path":[],"message":"Unrecognized key: \"voice_id\""}`. The setting to fix: `get_voice_packet` accepts the argument `voice` (not the `voice_id` that `search_voices` returns), and its `format` setting accepts only `post|reply|explanation|thread` with **no `email` option**, even though the same packet exposes a separate `platform` setting. This is reproducible: sending the identical `voice_id`/`email` body to the endpoint returns the identical error. A caller cannot see the real argument names or the real format list before calling, so the first call is guesswork.
- **One change.** Accept `voice_id` as an alias for `voice` (and list each tool's argument names and enum values in its `inputSchema` description), or, failing that, return a single correction that names the accepted argument and its enum instead of the raw three-error zod dump. That would have saved the failed first round trip on this run and removes the only real friction I hit.
